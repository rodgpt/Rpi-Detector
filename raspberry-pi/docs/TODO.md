- [x] **[SW] No synthetic source could soak-test the real pipeline at a chosen rate** DONE (2026-09-22) — with a constant signal, `psd_tonal` is all-or-nothing (`tone`/`impulse` fire every window, `noise`/`silence` never; thresholds just move where the cliff is, not its shape). There was no way to prove capture→classify→queue→push survives *unattended over time* without either flooding (~17k events/day) or using `inject_event.py`, which bypasses capture and classification entirely — the wrong tool when the question is whether the real pipeline holds up, not whether transport does. Added `synthetic:sporadic`: background noise, with a full tone burst on a single randomly-chosen 5 s window at Poisson-distributed intervals (`OCEANKIND_SYNTHETIC_SPORADIC_MEAN_S`, default 720s/12min). The window decision is made once per window and held for its full duration — never diluted across a boundary. Verified against the real code, not asserted: a 200h simulated run landed within 6% of the target mean interval (normal Poisson variance), and the real `psd_tonal.detect()` fires cleanly on the chosen window (`score: 1.0`) and stays silent on every other one.
  - **Caught by the simulation, not by review:** the first implementation had an off-by-one — `window_idx` was computed from `self._frame_pos` *after* incrementing it for the current block, while the block's own samples (`t`) used the position *before* incrementing. The redraw for a new window therefore fired one block (0.1s) early, on the *last* block of the outgoing window rather than the first block of the incoming one — corrupting boundaries and, in testing, making the diagnostic print (read after generating a window) report the *next* window's decision instead of the one that actually governed the samples just generated. Fixed by keying the window index off `block_start` (the position before increment). Left as a comment in `capture.py` since the same pre/post-increment trap exists nowhere else in the file today but would recur in any new per-window synthetic-source logic built the same way.
  - **Also corrected while verifying:** BENCH.md's "Controlling the event rate" table claimed `synthetic:impulse` "fires every window." Tested against the real detector: it fires **nothing**, 0/20 windows, matching `psd_tonal.py`'s own F-21 comment (an impulse scores ≤0.2, well under `score_min`'s 0.60 default) — it's built for `ml_mfcc`, not enabled on this bench. The §0.1 "reduce the load" advice suggesting `impulse` for "far fewer detections" was accidentally directionally right (it does reduce load — to zero) for the wrong stated reason. Both corrected; `synthetic:sporadic` is now the documented way to get "some" real detections.
- [x] **[Net] `push.py` masked a Cloudflare edge block as a fabricated "site mismatch"** DONE (2026-09-22) — device pushes to `marfutura.buenalynch.com` consistently got `403`, logged as "site no coincide con el registro (aprovisionamiento)". Site, device and key all checked out — `docker compose exec db psql` on `cepelynvault` showed an exact match, and a manual `curl` with the real device key reached the real backend cleanly (`400` for an incomplete test payload, not `403`). The backend's own access log never showed the push at all — for any of it, ever. Root cause: `push.py` built its request with `urllib.request` and never set a `User-Agent`, so it sent the bare default `Python-urllib/3.13` — a signature Cloudflare Bot Fight Mode blocks at the edge (`error code: 1010`) before the request reaches the container. Confirmed by reproducing the exact header with `curl -A "Python-urllib/3.13"`: same `403`, Cloudflare's own plain-text body, no `cf-cache-status`. `push.py`'s status-code handler only ever branched on the numeric code and printed a fixed guess per branch — it never read the response body, so a real backend rejection and an edge block were indistinguishable from the device's own logs, and the wrong theory (site/registration) ate most of the debugging time. Fixed both defects together: `push.py` now sends `User-Agent: oceankind-device/<__version__>` (sidesteps the block) and logs the actual response body — truncated to 500 bytes — on every `400`/`401`/`403`/`5xx` instead of a canned message. BENCH.md §"Reading failures" now says explicitly that a `403` needs the log line read, not assumed, and that an absent line in `docker compose logs backend` for a push the device reports as rejected means it never arrived. Worth a general lesson for any future outbound HTTP from this device: always set a real User-Agent, and never trust a status-code-to-cause table without the body when a CDN or WAF sits in front.

- [x] **[Prov] OTA reported success while changing nothing; no rollback** DONE (2026-09-04) — found tracing the two-folder layout during bench provisioning. Four defects, two of them silent. (a) `update_oceankind.sh` pulled into `~/oceankind/code` and restarted the service, but systemd runs the *copy* at `~/oceankind/` — nothing installed the new code, so a "successful" OTA printed `✓ Actualización completada: abc → def` and kept running the old build. (b) The dependency step guarded on `$REPO_DIR/requirements.txt`; the file is at `raspberry-pi/requirements.txt`, so `[ -f ]` failed and deps were silently never updated. (c) No checkout existed — `setup.sh` never created one and never installed the script at `~/oceankind/update_oceankind.sh`, the path both its own header and `protect_sd.sh:145` tell operators to run. Rewritten around a verify-and-revert contract: git checkout auto-clones (repo is public, no deploy key), an explicit install step mirrors `setup.sh` §5, restart is verified for `SETTLE_S` (60 s default) requiring active **and** no restarts, failure reverts to the previous commit and re-verifies, and the bad SHA is recorded in `.ota_failed_sha` so an unattended unit never retries a commit that already broke it. Proven by `tools/ota_rollback_test.sh` — five scenarios, breaks an update on purpose, runs on a workstation with no Pi. Remaining hardware-only gaps in the open item above.
- [x] **[Ops] Liveness had no signal at all when storage was not configured** DONE (2026-09-23, D-018) — direct consequence of the bench's push-only configuration (see the open item above): with no Azure and no local storage bridge, `status.json` was never written anywhere, so the dashboard showed nothing for the unit and — the sharper finding, caught only by reading `silence.py` before assuming the fix — the backend's device-silence alerting had nothing to read either, meaning a unit in this state could die outright and never be flagged. A bench-only rsync-from-cepelynvault fix was considered and rejected: it needs inbound SSH to the device, which the production deployment model (`SERVER-INFRASTRUCTURE.md`) rules out categorically — devices are outbound-only, no inbound path ever. Built instead: `push.py:post_heartbeat()` POSTs the same `status.json` document to `POST /api/devices/heartbeat` on every heartbeat, unconditional on storage being configured. Deliberately **no retry and no spool** — unlike event push, a stale heartbeat has no value and retrying risks delivering one out of order after a fresher one already landed; a run of failures instead surfaces via a fail-streak counter in `health.degraded_reason`/`health.heartbeat_fail_streak`. The backend enforces the no-regression guarantee independently (silently ignores any POST whose `last_seen` is not strictly newer than what is stored), and keeps every accepted heartbeat in a `DeviceStatusHistory` table, not just the latest. `GET /api/sites/{site_id}/status` and `silence.py` were both changed to compare blob-storage `status.json` against the Postgres reading and use whichever is fresher — additive, not a replacement, so the pre-existing 14 `silence.py` tests and the whole 98-test backend suite still pass unchanged alongside 11 new heartbeat tests. Full design and rationale: `DATA-CONTRACT.md` §Device heartbeat, `DECISIONS.md` D-018.
